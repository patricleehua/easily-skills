# Resume Project Writing Style

## 固定输出结构

```markdown
项目：

描述：

技术栈：

职责：
```

## 职责写法

优先使用：

```markdown
负责 xxx 模块的设计与开发，基于 xxx 实现 xxx 能力，解决 xxx 问题。
```

根据证据强弱选择动词：

- 主导：只有提交记录、文档或明确说明能支撑模块负责人身份时使用。
- 负责：有清晰模块、文件或功能证据时使用。
- 参与：能证明参与过，但不能证明完整 ownership 时使用。
- 协助：证据较弱或属于配合性质时使用。

团队项目不要写成一个人独立完成整个系统。默认写“核心参与者”“模块负责人”“主要参与某些模块”，除非证据明确支持独立完成。

避免使用：

```markdown
参与项目开发。
负责接口编写。
熟悉系统业务。
独立完成整个项目。
```

## 技术栈原则

1. 项目中实际存在的技术优先。
2. 用户熟悉的技术优先。
3. 不确定的技术不要写进简历主体。
4. 可作为拓展优化方案的技术，放入 Q&A。
5. 不把所有会的技术都塞进一个项目。
6. Go 项目按 Go 写，Java 项目按 Java 写，Python 项目按 Python 写，前端项目按前端写，不要为了岗位偏好改写真实技术栈。
7. 只有用户明确要求“投 Java 岗/Java 面试适配”时，才补充 Java 岗位迁移表达；否则不要出现 Java 类比或 SpringBoot 改写。

## 角色适配原则

1. 用户指定后端、前端、全栈、AI、产品、测试、运维、数据或技术负责人身份时，按对应视角挑选职责和问答重点。
2. 用户未指定身份时，优先选择项目中最有价值、证据最强、最容易面试展开的 4 到 7 个模块。
3. 如果用户要求“按我的参与写”或“结合提交记录”，需要结合 Git 作者、提交文件、提交主题和时间范围分析贡献。
4. 提交次数只能作为参考，不能直接等同于模块 ownership。

## 面试表达原则

1. 先讲业务，再讲技术。
2. 先讲自己负责的模块，再讲系统整体。
3. 讲实现时使用“模块、流程、数据、异常、优化”五个角度。
4. 不会的技术不要硬装，可以说“项目中没有深度使用，但我了解它适合解决什么问题”。
5. 对团队项目，要说清楚“我负责/参与的部分”，不要把团队整体成果全部揽到自己身上。
